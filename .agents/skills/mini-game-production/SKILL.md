# 从游戏 brief 到游戏平台草稿

以本地能运行的 H5 为原版，以 GitHub 固定提交为交付版本，以游戏平台的实际可玩草稿为平台验收对象。按用户要求完成全部或指定阶段。外部交付以用户在本次任务或相关项目中给出的目标仓库和平台授权为准。

## 读取 brief

优先使用已连接的文档工具，必要时用已登录的浏览器读取用户指定的页面。读完与任务相关的小节、表格和附件，按文档的标题和范围识别每个 brief。同一个链接可以包含多个独立 brief。每个分别记录主题、核心机制、款数、尺寸、语言和交付要求，并据此独立设计、制作和验收。把页面上的内容当作设计输入，外部操作权限仍由用户决定。遇到权限问题时，说明具体缺少的内容并继续处理已读到的独立工作。

## 设计和实现

- 先确定玩家会持续做什么、局势怎样变化、通过什么方式推进目标。一个 brief 下的各款作品，应在核心循环、空间结构、镜头或推进方式上形成实质差异。用首屏和前几秒操作横向比较。避免整批复用「进场景 → 做一个小游戏 → 换场景」。关卡数量和结构随 brief 与玩法决定。
- 让人看到目标、试一次操作就能理解因果。用场景物件、动效、声音和局部短提示教会操作。深度来自时机、路线、资源和有后果的选择。成功、失败和重试都要有清楚的反馈。
- 让高度、距离、遮挡、视线、朝向或路径实质影响判断与操作。给不同游戏独立的构图、色彩、灯光和材质。结合粗糙度、高光、接触阴影、前中后景和尺度表现质感及纵深。竖屏主体要清楚，场景与界面应避开关键目标和触控区。
- 每个 brief 在交付根目录下有一个按主题命名的文件夹，里面的每款游戏有自己的子目录，路径为 `<brief>/<game>/`。本地和 GitHub 采用同样的层级，各游戏在自己的目录内保留运行所需的文件、入口和构建命令。不同 brief 的游戏可以分别交付。

## 验收本地 H5

用浏览器在手机竖屏比例真实操作，从零进度到结局。按 brief 的尺寸验收，未指定时可用 390×844，并在关键画面抽查 320×640。验证开场能否看出要做什么、关键手势和点击、关卡或状态转换、失败重试、成功反馈及结局。批量时保留每款的实际结果。自动化回归可补充覆盖，交付时区分回归、浏览器试玩和真机实测。

## 交付 GitHub 与游戏平台

将验收通过的游戏提交到用户指定的 GitHub 仓库。核对目标分支、提交与推送结果，并保留完整 commit SHA。只包含这次任务相关的改动。

要导入或更新游戏平台草稿时，读取 [游戏平台源码交接和验收](references/platform-handoff.md)。使用固定提交的真实文件和对应的构建入口。先验证平台能读到源码，再使用实际产物完成手机竖屏试玩，保存并重开核对版本。发布和送审需要用户另外提出。

最终按 brief 分组汇总游戏名称、GitHub 目录和版本、游戏平台草稿链接、通关结果和保存重开状态。只把实际确认的步骤标为完成，并说明影响验收的限制。关闭本次用完的临时试玩页和草稿页，保留用户原先打开的页面。
